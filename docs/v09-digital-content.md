# V0.9 digital conversation content

Email and messaging load through the existing `GenesysCloudConversationSource`, shared by the interactive token relay and server client credentials. They return ordinary provider-neutral Conversations. Policy, sampling, grouped/conditional evaluation, review and calibration remain channel-independent. No digital evaluator or provider-specific scoring was introduced.

## Official contract and retrieval

Current [Genesys JavaScript SDK API contract](https://github.com/MyPureCloud/platform-client-sdk-javascript/blob/master/build/docs/ConversationsApi.md) and [generated model declarations](https://github.com/MyPureCloud/platform-client-sdk-javascript/blob/master/build/index.d.ts) were inspected on 1 October 2026. Email preview listing returns `EmailMessagePreviewListing.entities`; each ID retrieves `EmailMessage` from `GET /api/v2/conversations/emails/{conversationId}/messages/{messageId}`. Complete direct content is preferred and avoids recording calls. Empty/incomplete/unavailable direct content can use the existing Recording EML/PostalMime fallback; authorization, rate-limit and size failures do not trigger redundant alternate retrieval. A Recording discovery 404 no longer prevents direct email retrieval. A paginated/incomplete preview listing is treated as incomplete rather than following arbitrary provider URLs; EML fallback may resolve it.

Messaging uses `GET /api/v2/conversations/messages/{conversationId}`. Authoritative IDs are `MessageConversation.participants[].messages[].messageId` (`MessageMediaParticipant`/`MessageDetails`). `POST .../messages/bulk` sends arrays of only those IDs, at most 100 at a time, and reads `TextMessageListing.entities[]` (`MessageData`). Missing batch entries or unsupported bulk endpoints use conversation-bound individual GETs. IDs, conversation identity, duplicates and complete retrieval are checked. Successful direct retrieval means content for the returned inventory; provider-free fixtures cannot establish that a historical provider inventory includes every message.

The [SDK MessageData model](https://github.com/MyPureCloud/platform-client-sdk-go/blob/master/platformclientv2/messagedata.go) supplies timestamp, direction, createdBy and normalizedMessage. Participant purposes are authoritative; createdBy and inbound direction disambiguate repeated IDs. Unknown/conflicting identities fail closed. Explicit [originatingEntity](https://github.com/MyPureCloud/platform-client-sdk-go/blob/master/platformclientv2/conversationnormalizedmessage.go) bot markers remain bot context even on an agent-purpose communication. Speaker adds compatible `bot` and `system` values; agent/customer conversations are unchanged. Stable timestamp/ID ordering, sender identity and readable labels are retained.

Plain email text wins over HTML. HTML conversion skips scripts, styles, images and link targets without executing or fetching resources. Quoted email history remains in each individual message; no brittle quote stripping. Messaging supports Text/Structured text and documented text bodies, quick replies, button responses, card title/description/action labels and carousel labels. Receipt/event/media-only entries produce counts outside message text. No attachment URL/content, raw payload, signed media URL or archive is persisted. Non-text context is not presented as evaluated content.

Messaging content GET/bulk requires **conversation:message:view OR conversation:webmessaging:view**, plus applicable context/division access. Denial reports those alternatives; no roles or permissions are changed. Email endpoints document no additional endpoint-specific permissions. The authenticated relay keeps `/email` compatibility and adds `/digital`, enforces the existing user allowlist and uses only the caller's token; automation credentials and Jev secrets are never exchanged with browsers.

## Bounds and historical fallback

Maximum 500 digital messages, 100 KB UTF-8 text per message, 1 MB normalized aggregate text, 5 MB streamed JSON response, 10 MB aggregate JSON per retrieval path, 20-second request timeout, and bounded identity metadata. EML keeps its 2 MB download, 5 MB aggregate download and 25-recording bounds. Bound violations discard partial content and produce visible diagnostics; nothing is silently truncated. Email subjects/sender fields and message counts are validated as part of normalized bounds.

If historical direct messaging IDs/content are unavailable, bounded Recording discovery checks for `media=message`. ZIP decoding remains **unsupported**: documentation establishes `messageFormatId=ZIP`, but no trustworthy internal archive structure is established. The application neither fetches that ZIP nor invents a parser; diagnostics distinguish a discovered message recording from no recording. This scope can expand only with official or observed archive evidence and safe deterministic fixtures.

## Cache and evidence

The shared identity-scoped IndexedDB cache still uses 15-minute search and 24-hour content TTLs; explicit Refresh bypasses content cache and Disconnect clears it. Whitelist copying retains only normalized fields and safe diagnostics, including sender IDs and non-text counts. Jev serialization receives the same Conversation schema, including bot/system context; unavailable or rejected content has no transcript to evaluate.

Deterministic tests cover direct email retrieval/HTML/order/fallback/404, messaging ID inventory/batching/individual fallback/roles/structured content/media-only/limits/permission/historical availability, browser/server equality and ordinary policy/conditional/review/calibration behavior. Existing EML, voice and identity cache regressions remain. `digitalProof.mjs` is read-only: discover at most five completed candidates per channel and load at most two; log only endpoint statuses, counts and safe diagnostics, with zero Jev or Firestore operations. Deployment/live proof and exact release evidence belong in [the existing checkpoint](v061-control-plane-cache.md#v09-digital-content-checkpoint).
