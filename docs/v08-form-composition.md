# V0.8 form composition

Forms keep `questions` as their canonical flat collection, with globally unique form-local IDs and existing question weights. Optional ordered `groups` describe structure, applicability and reusable provenance; questions use `groupId`. Effective order is group order, then flat collection order within each group. Ungrouped questions appear in General. Group scores are display/analytics weighted averages, never another weight multiplier. `sourceGroupWeight` remains inert provenance.

Legacy definitions and historical EvaluationRecords are never bulk rewritten. Readers derive virtual groups from `section`, including General for missing sections. `nextFormVersion` materializes those sections in the new draft only. The actual Customer Service v17 remains unchanged; new v18 drafts materialize Opening, Assisting The Customer, Call Handling Skills, and Compliance & Closure, preserving disabled questions. Published forms use the same rich grouped cards, instructions and rubrics read-only. Source-review acknowledgement remains inert.

## Applicability and dependencies

Provider-neutral conditions support interaction channel/queue/direction/topic (`equals` or `in`), prior Noul Yes/No or Choice option keys (`equals` or `in`), and normalized prior question credit (`less_than` or `greater_than_or_equal`, threshold 0–1). Legacy metadata `equals` and prior-question `outcomes` fields remain accepted. Score outcomes require credit comparisons, rather than rubric labels. Missing metadata, skipped referenced questions and null credit make a condition false. Conditions compare normalized outcomes/credits, never raw Noul probability or human review answers.

Effective applicability is group AND question applicability. A question can reference only an earlier enabled question in effective order; a group can reference only questions in earlier groups. Asset-internal conditions reference earlier questions in that same template. Validators explain missing, self, forward/cyclic, disabled and incompatible references. Existing disabled dormant question fields remain readable without making old published forms invalid; enabling them brings their dependencies under validation.

`domain/formComposition.ts` owns validation, ordering, maximum wave depth, applicability, wave construction, explicit skips and aggregate scores. It accepts an `evaluateQuestions(request)` callback; Jev adapters only evaluate each typed subset. Ready questions are batched in one request per wave. Static false conditions are resolved without a request, and newly known dependencies unlock the next batch. Unconditional forms normally use one request; all-skipped forms use zero. No skipped question is sent to the provider. Missing or inconsistent wave answers fail the logical evaluation.

Results without `status` mean ANSWERED for historical compatibility. New SKIPPED results have a reason (`disabled`, `group_condition_false`, `question_condition_false`), no raw answer, null credit and null contribution. Skips contribute no counted weight or critical failure. Null-credit answered options retain the existing unscored behavior. Overall/group scores are sum(credit × question weight) / sum(scored answered question weights), or null if no weight counts.

## Costs, persistence and failures

A form evaluation remains one logical assignment. Policy preview and Form Test show assignment count separately from maximum Jev requests, bounded by dependency depth across the selected forms/conversations. Production records store `providerRequestCount` and `groupResults`; runs/tests store maximum/actual provider attempts separately from evaluation counts. Zero-call results use `not-requested` provider/model provenance. Historical request counts that were never persisted are labelled Not recorded (legacy), and authored synthetic demo records report zero provider requests.

Manual, scheduled/manual policy and durable/browser Form Test paths share the orchestrator. Production reserves the existing evaluation slot before the first wave. Each request attempt is recorded before the provider call. A charged or uncertain failure leaves the logical slot reserved; blind retry never restarts earlier waves. Form Test likewise creates its durable test ID first and returns that same run on recovery, including partial/uncertain progress. Attempt counts include failed/ambiguous requests and do not assert that a response was received or a charge confirmed. This is bounded progress accounting, not a durable resumable wave engine. Browser development sandboxes retain their pre-existing local-only durability boundary.

Form Test records remain embedded only in `formTestRuns` with purpose FORM_TEST, excluded from production stores and analytics. Output shows applicable/skipped groups, answered/skipped questions, group/overall scores and actual requests.

## Reusable library

`QuestionGroupAsset` has stable family/version identity, asset-local question IDs, name/description, optional metadata group applicability, timestamps and DRAFT → PUBLISHED → RETIRED lifecycle. New versions get new document IDs; published/retired definitions cannot be edited or returned to draft. The authenticated table-first Question Groups page supports draft editing/saving, publish, new-version editing, retire, question preview and form-use counts within loaded configuration. Disconnected authoring is browser-local; connected explicit saves use the durable service.

Firestore stores `questionGroupAssets`. Store methods use transactions for published immutability and family/version uniqueness; GET library reads are paginated at at most 100 items, with a 1,000-version editor bound. The explicit provider-free `server-dist/seedGroupAssets.mjs` operation defaults to preview; `--apply` creates four missing starter templates only and never replaces existing documents. It does not write forms, policies, schedules, evaluations or reviews.

Insertion copies a published asset into the form, namespacing question IDs by a unique group instance. Internal conditions are remapped; sourceAsset stores family/asset/version and each question records its asset-local source ID. Runtime always uses the form snapshot and never fetches asset documents. Editing/publishing a template cannot change its consumers.

Draft/testing forms may explicitly update a group to a selected newer published version. Updates retain the group instance and matching form-local question IDs, copy template name/description/questions, add/remove safe questions, and remap internal conditions. The instance's own applicability condition is retained during update. External dependencies (including dormant ones) and critical designations block unsafe removals/incompatible changes with an explanation. Detach retains the current snapshot and removes asset provenance. Saving a local group creates a new DRAFT asset; saving a customized asset instance creates a new DRAFT family version. Cross-group dependencies cannot become self-contained templates. Published forms cannot update/detach.

## Review and analytics

HumanReview uses the complete original EvaluationRecord snapshot and its effective group order, labels groups, shows skipped questions, and refuses human answers for skips. Completion requires only applicable evaluated questions. Historical V0.7 records/reviews remain readable; AI results stay immutable. Calibration excludes skips from agreement, credit and confidence denominators and question/type cohorts. Question quality analytics expose answered/applicable versus skipped counts; ordinary pass rates use scored answered results. Group analytics show form/version, evaluation count, applicable count, average display score and critical failures. FORM_TEST never enters these calculations.
